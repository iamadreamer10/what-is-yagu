## 1. 기술스택 (D-009, D-017~D-022, D-031)

### 1.1 고르는 기준

기술스택 자체는 이 프로젝트의 우선순위가 아니다. 가장 효율이 좋은 조합을 고른다. (D-017)
- AI(Claude Code)가 잘 다루는 것
- 운영 부담이 적은 것 (서버·도구 개수를 늘리지 않는다)
- AWS 무료 플랜 크레딧 안에서 운영할 수 있는 것

### 1.2 스택

| 영역 | 선택 | 결정 |
| --- | --- | --- |
| 백엔드 | Java 21 + Spring Boot (Spring AI와 호환되는 최신 안정 버전) | D-009, D-022 |
| 프론트엔드 | React + Vite (SPA). 정적 파일을 nginx로 서빙 | D-018 |
| DB | PostgreSQL + pgvector. 형태가 바뀌는 데이터는 JSONB | D-019 |

| CI/CD | GitHub Actions. develop은 CI만, main은 CI + EC2 배포 | D-021, D-031 |


## 2. 산출물 형식과 도구 (D-014, D-016, D-023~D-026, D-030, D-032)

### 2.1 원칙

- 산출물은 레포 안에 텍스트로 둔다. 다음 단계의 AI가 그대로 읽을 수 있어야 한다.
- 도구보다 형식을 먼저 정한다. 도구는 형식을 지키는 것 중에서 고른다.
- 설계는 두 깊이로 만든다 (D-016): 1주차에 모든 기능의 개요와 전체 설계 초안, 기능마다 상세.

### 2.2 산출물별 형식

| 산출물 | 형식 | 둘 곳 |
| --- | --- | --- |
| 모든 기능 개요 + 규모 | Markdown | `docs/design/features.md` |
| 기능 상세 명세 | Markdown (템플릿: `docs/templates/`) | `docs/specs/<번호>-F1-<이름>/spec.md` |
| ERD | Mermaid `erDiagram`. 그림은 한 곳에만 | `docs/design/erd.md` |
| API 전체 목록 | Markdown 표 | `docs/design/api.md` |
| API 상세 | OpenAPI 3 yaml (원본). Notion은 보기용 사본 | 기능 폴더 `api.yaml` / Notion (`docs/templates/notion-api-sync.md`) |
| 화면 목록과 흐름 | Mermaid flowchart + 화면 설명 | `docs/design/screens.md` |
| 와이어프레임 | Google Stitch 결과(HTML, 캡처) + 프롬프트 | 기능 폴더 `wireframe/` |
| 배포 아키텍처 | Mermaid flowchart | `docs/design/architecture.md` |
| 작업 | GitHub Issue (템플릿: `.github/ISSUE_TEMPLATE/task.md`) | GitHub |

### 2.3 와이어프레임 (Stitch) 규칙 (D-023)

1. 입력은 명세다. `screens.md`나 기능 명세의 화면 설명으로 프롬프트를 쓴다.
2. 프롬프트를 `wireframe/prompt.md`에 남긴다.
3. 내보낸 HTML과 캡처를 `wireframe/`에 저장한다.
4. 기준은 명세다. 디자인과 명세가 다르면 명세를 먼저 고치거나 다시 생성한다.

### 2.4 Notion (D-025, D-027, D-032)

- 레포의 OpenAPI 파일이 원본이다. 기능 상세 설계를 승인할 때 AI가 Notion에 옮긴다. Notion에서는 직접 고치지 않는다.
- Notion은 API 명세만 다룬다. 진행 상태는 GitHub Issues에서만 관리한다.

### 2.5 폴더 구조 (D-026)

```
docs/
├─ plan.md, decisions.md   전체 계획, 결정 목차
├─ principles.md           대원칙 (이 문서)
├─ templates/              명세 템플릿, Notion 동기화 규칙
├─ design/                 지금 상태: 전체 설계
├─ specs/<번호>-<작업명>/   작업 단위: plan.md, decisions.md (과정 기록)
│                          기능 단위면 spec.md, api.yaml, wireframe/ (지금 상태)
└─ eval/                   평가 질문 세트
```

- 지금 상태(`design/`, 기능 폴더의 spec·api·wireframe)는 항상 최신으로 고쳐 쓰고, 왜 바뀌었는지는 결정 기록에 남긴다.
- 과정 기록(plan.md, decisions.md)의 결정은 지우지 않는다.

## 3. 테스트 (D-028)

### 3.1 목적

AI가 코드를 바꿔도 안전하다는 것을, 사람이 매번 코드를 다 읽지 않고도 확인할 수 있게 한다.

### 3.2 테스트 층

**이 층에서만 잡을 수 있는 문제가 있을 때만 테스트를 쓴다.** 형식적으로 모든 층에 테스트를 넣지 않는다.

| 층 | 뜻 (무엇까지 진짜로 실행하나) | 목적 (무엇을 지키나) | 이 프로젝트 예시 | 비용·시점 |
| --- | --- | --- | --- | --- |
| **L1 단위** | 클래스나 함수 하나만. DB, 네트워크, LLM 없음 | 규칙과 계산이 맞는지 빠르게 확인 | 팀 매칭 점수 계산. "검색 점수가 기준보다 낮으면 근거 없음으로 판정" 규칙 | 0원, 수 초. 매 수정 |
| **L2 통합** | 우리 코드 + 실제 DB(pgvector, Testcontainers). HTTP는 거치지 않음 | 쿼리, 저장, 벡터 검색이 실제 DB에서 동작하는지 | 질문 로그 저장·조회. 유사도 쿼리가 가까운 문서 순으로 나오는지 | 0원, 수십 초. 매 PR |
| **L3 API** | HTTP 요청부터 응답까지 전부 (컨트롤러 → 서비스 → DB). LLM만 가짜 | 사용자(화면)와의 약속(명세, 수용 기준)을 지키는지 | 근거 없는 질문이면 `UNKNOWN`. 빈 질문이면 400 + traceId | 0원, 수십 초. 매 PR |
| **L4 검색 평가** | 질문 → 근거 문서 검색까지만. 설명을 만드는 LLM은 부르지 않음 | 뉴비의 묘사형 질문에 맞는 근거 문서를 찾는지 (RAG 품질) | "힘없는 땅볼인데 왜 환호해?" → 진루타 문서가 상위 3개 안에 있는지 | 질문 임베딩 비용만 조금. 근거 문서나 검색 방식이 바뀔 때 |
| **L5 설명 평가** | 진짜 LLM이 만든 최종 설명 | 설명이 정확하고 쉬운지, 근거가 없으면 모른다고 하는지 | 평가 질문 세트의 답변을 기준표로 채점 + 사람 검수 | LLM 비용. 프롬프트나 모델이 바뀔 때 |
| **정적 분석·보안** | 코드를 실행하지 않고 검사 | 취약점, 비밀값 노출, 코드 품질 | 키가 코드에 들어갔는지 검사 | 0원. 매 PR (3~4주차 도입) |

E2E(브라우저 화면 테스트)는 두지 않는다. 화면이 단순해 비용 대비 효과가 낮다.

**어느 층인가? 판단 순서**

```
진짜 LLM 응답을 봐야 판단할 수 있나?        → 예: L5
근거 문서를 잘 찾는지가 관심사이고,
결과가 통과/실패가 아니라 비율(적중률)인가?  → 예: L4
HTTP 요청·응답(명세, 상태 코드)을 확인하나?  → 예: L3
실제 DB가 있어야 의미가 있나?                → 예: L2
그 외 (규칙, 계산)                           → L1
```

**헷갈리기 쉬운 경우:** "근거가 없으면 모른다고 한다"는 세 층에 나올 수 있다. 확인하는 것이 다르다.
- L1: 판정 규칙이 맞는지 (점수 0.3이면 근거 없음)
- L3: 사용자에게 약속한 응답이 나오는지 (`answerType: UNKNOWN`, `sources: []`)
- L5: 실제 LLM이 정말로 모른다고 말하는지 (지어내지 않는지)

### 3.3 수용 기준과 우선순위

- 기능 상세 명세에서 수용 기준과 테스트 목록을 먼저 뽑는다. 이때는 우선순위를 매기지 않는다.
- 기능이 구체화되면 각 항목에 우선순위를 매긴다. 4단계 작업 생성 때 P0부터 작업으로 만든다.
  - P0: 반드시 테스트한다
  - P1: 가능하면 테스트한다
  - P2: 생략할 수 있다
- 테스트 이름에 수용 기준 ID(예: `AC-F1-03`)를 붙인다. 명세 → 테스트 → 평가 질문이 이어지게 한다.

### 3.4 AI 수정 → 검증 패턴

```
① 명세의 수용 기준 (AC-F1-01 …)
② 테스트 먼저 작성 (수용 기준 ID를 테스트 이름에)
③ AI가 코드 수정
④ 영향 분석: 바뀐 코드를 쓰는 곳과 관련 테스트를 AI가 정리
⑤ 관련 테스트만 먼저 실행 → 실패하면 ③으로 (최대 3번)
⑥ (선택) 리팩토링 제안: 우선순위, 장단점, 판단 기준을 받고 사람이 고른다
⑦ PR → CI가 전체 테스트 실행 (L1~L3, 필요하면 L4)
⑧ 사람 승인 → main 병합 → 자동 배포
```

- 영향 분석과 테스트 선택을 위해 코드는 기능별 패키지로 나누고, 테스트에 기능 태그(JUnit `@Tag("F1")`)를 단다.
- 관련 테스트만 먼저 실행하는 것은 AI의 수정·확인 반복을 빠르고 싸게 하려는 장치다. 최종 확인은 CI가 늘 전체로 한다.

### 3.5 AI 규칙

- 테스트를 통과시키려고 테스트를 지우거나 약하게 고치지 않는다. 고쳐야 하면 이유를 말하고 승인받는다.
- 수정 후에는 관련 테스트를 실행하고 결과를 보고한다.
- 같은 문제로 세 번 고쳐도 실패하면 멈추고 원인을 보고한다.
- main에 직접 반영하지 않는다. PR, CI 통과, 사람 승인을 거친다. (GitHub 브랜치 보호로 강제)

### 3.6 토큰 절약

- 기능 태그로 관련 테스트만 실행한다.
- 테스트 출력은 실패한 테스트의 요약만 보이게 한다. AI는 전체 로그가 아니라 실패 요약부터 읽는다.
- API 테스트(L3)는 가짜 LLM을 쓴다. 진짜 LLM은 L5에서만 부른다.
- L4·L5는 필요할 때만 실행한다. 근거 문서는 바뀐 것만 다시 임베딩한다.
- 테스트 수는 우선순위(3.3)로 필요한 만큼만 유지한다.

### 3.7 API 테스트 규칙

API 테스트는 JUnit으로만 한다. Postman과 `.http` 파일은 쓰지 않는다. 손으로 확인할 때는 springdoc의 Swagger UI를 쓴다.

1. 테스트 하나 = 수용 기준 하나. 이름에 AC ID를 붙인다.
2. 성공만큼 실패도 테스트한다. 명세의 Status 표 한 줄이 테스트 하나다.
3. 응답 모양은 `api.yaml`로 자동 검사하고, 테스트는 의미 있는 값만 확인한다.
4. LLM은 가짜로 바꾼다.
5. 실제 DB(Testcontainers)를 쓰고, 테스트마다 데이터를 새로 넣는다.

### 3.8 에러 로그

- 테스트 실패 로그: 실패 요약만 출력한다 (3.6).
- 서비스 에러 로그: 에러 응답에 추적 ID(traceId)를 담고, 서버 로그에도 같은 ID를 남긴다. 트러블슈팅 기록의 근거로 쓴다. 테스트는 "에러 응답에 traceId가 있다"까지만 확인한다.
- 공통 에러 응답 형식은 API 설계(1주차 작업표 3-4)에서, 로그를 모을 곳은 아키텍처(3-5)에서 정한다.

### 3.9 나중에 정할 것

- L5 자동 채점에 LLM-as-judge를 쓸지: F1 설계 때
- 정적 분석·보안 도구: 3~4주차

## 4. AI 사용 원칙 (D-029, D-030, D-031)

### 4.1 서비스의 LLM 호출 (세부는 F1 설계에서)

| 원칙 | 내용 |
| --- | --- |
| 검색이 먼저, LLM은 나중 | 근거 문서 검색 점수가 기준보다 낮으면 LLM을 부르지 않고 "모르겠어요"로 답한다. 토큰을 아끼고 "근거가 없으면 모른다" 원칙을 코드로 지킨다 |
| 모델은 일에 맞게 | 질문 분류·되묻기 판단은 가벼운 모델. 설명 생성도 가벼운 모델로 시작하고, L5 평가에서 기준에 못 미칠 때만 고성능 모델로 올린다 |
| 프롬프트 캐시 | 바뀌지 않는 부분(역할, 규칙)을 앞에, 바뀌는 부분(질문, 근거)을 뒤에 둔다 |
| 넘기는 근거 양 제한 | 근거 문서는 상위 몇 개, 필요한 섹션만 넘긴다 |
| 요청마다 토큰 기록 | 질문 로그에 사용 토큰을 남긴다. 지표 기반 개선의 근거로 쓴다 |
| 사용량 상한 | 사용자별 요청 제한과 월 예산 상한을 둔다 |

### 4.2 개발용 AI (Claude Code, Pro 한도)

- 세션은 작업 하나 단위로 짧게 쓴다. 대화가 길수록 매 요청에 다시 읽는 양(캐시 읽기)이 커진다.
- 필요한 문서만 읽는다: CLAUDE.md → 해당 기능 폴더 → `docs/design/`.
- 모델은 일에 맞게 고른다. 단순 작업(문서 정리, 커밋)은 가벼운 모델, 설계·어려운 디버깅은 고성능 모델.
- 병렬 작업(서브에이전트)은 정말 필요할 때만 쓴다.

### 4.3 작업 관리: 판단은 사람, 입력은 AI

| | 나 (판단) | AI (번거로운 조작) |
| --- | --- | --- |
| 작업 나누기 | 기준을 정하고 직접 나눈다 | — |
| Issue 등록 | 제목과 범위를 알려 준다 | 템플릿대로 작성, 라벨·보드 등록 (`gh`) |
| 진행 중 | — | 브랜치 생성, PR 작성, 체크리스트 체크, 보드 상태 이동 |
| 잘 되었는지 | 완료 판단, 승인·병합 | 테스트 결과와 수용 기준 충족 여부를 보고만 한다 |
| Issue 닫기 | 병합하면 자동으로 닫힌다 | 직접 닫지 않는다 |

- 진행 관리는 GitHub Issues + Projects 한 곳에서 한다. 보드는 스터디 주간 보고(목표 대비 결과, 한 일과 증거)를 뽑을 수 있게 주차 단위로 맞춘다.
- 템플릿: Issue는 `.github/ISSUE_TEMPLATE/task.md`, PR은 `.github/pull_request_template.md`.
- 라벨: 기능(`F1`…), 종류(`feat`·`fix`·`test`·`docs`·`chore`), 우선순위(`P0`·`P1`·`P2`).

### 4.4 AI 사용량 기록

- PR마다 "AI 사용 기록"을 필수로 남긴다: AI 호출 횟수, 대화 턴 수, 토큰(입력·캐시 저장·캐시 읽기·출력), 작업 유형, 사람이 직접 고친 부분.
- 숫자는 `python tools/ai-usage.py --since <브랜치를 만든 시각>`으로 AI가 채운다.
- 목적: SDD의 효과(명세 유무에 따른 차이)를 숫자로 비교하고, 스터디 주간 기록의 증거로 쓴다.
- 한계: Pro 한도 사용률(%)과는 다른 숫자다. 개발용 AI만 잰다(서비스 LLM 토큰은 4.1대로 앱이 기록). Claude Code 로그 형식이 바뀌면 스크립트를 고친다.

### 4.5 브랜치

```
feat/12-요약 ─PR→ develop ─(릴리스)→ main ─→ EC2 자동 배포 + 버전 태그
                 CI만 실행           CI + 배포
```

- 작업 브랜치: `feat/`, `fix/`, `test/`, `docs/`, `chore/` + Issue 번호 + 요약
- 기본 브랜치는 `develop`으로 한다. PR의 `Closes #번호`는 기본 브랜치에 병합될 때만 Issue를 닫는다.
- 릴리스(develop → main)는 내가 결정한다. 첫 릴리스는 `v0.1.0`.
- main과 develop 직접 반영 금지(브랜치 보호)는 대원칙이 완료된 뒤부터 적용한다. 그 전까지 문서는 main에 바로 커밋한다.
