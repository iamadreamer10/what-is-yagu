## 2. 결정한 것과 이유

| 결정 | 고른 것 | 이유 |
| --- | --- | --- |
| 진행 방식 (D-014, D-016) | SDD 툴 없이 단계를 직접 구성. 기능 단위로 명세 → 설계 → 구현 | 설계를 다 끝내야 개발을 시작하는 구조를 피하고, 단계마다 사람이 승인한다 |
| 기술스택 (D-017~D-022) | Spring Boot(Java 21), React + Vite, PostgreSQL + pgvector, AWS EC2 1대 + Docker Compose, GitHub Actions | 효율 기준. 벡터 검색을 DB 하나로 해결하고, 무료 플랜 크레딧 안에서 운영한다 |
| 목적 (D-036, D-037) | "장면을 물으면 답해 주는 AI"에서 "뉴비가 알아야 할 정보를 묶어 보여 주고, 이해를 쌓아 가게 돕는 서비스"로 | 장면 질문은 일반 LLM에 물어도 된다. 야구는 한 번 궁금증을 풀고 끝나는 스포츠가 아니다 |
| 기능 제안 원칙 (D-038) | 목적과 고객에서 출발하지 않은 기능은 제안하지 않는다 | 기능부터 정하면 무리수를 둔다. "어느 고객의 어떤 문제를, 왜 일반 LLM으로는 안 되는가"를 먼저 밝힌다 |
| 설문 (D-043~D-045) | 지인 경로, 스스로 잘 모른다고 느끼는 사람. 야구를 잘 아는 사람은 짧은 별도 섹션 | 20년 본 내 감각 대신 뉴비의 답을 듣는다. 고인물은 "계속 보게 된 사람"의 경험으로 참고한다 |
| MVP 기능 (D-046, D-050, D-051) | F1 야구 정보, F2 재미로 정해 보는 응원팀, F3 상황 검색 | 뉴비가 막힌 곳: 숫자·기록 10/17, 팀·선수 8/17. 마음이 식은 이유 2위 "응원할 팀이 없어서" 5/17. "뭐라고 검색해야 할지 몰랐다" 4/17 |
| 우선순위 (D-052) | F1 → F2 → F3 | F2는 F1의 팀 정보만 있으면 되고, F3는 F1 문서가 쌓여야 쓸모 있다 |
| F3에서 AI의 역할 (D-053, D-054) | AI는 뉴비의 말을 알아듣는 데(질문 다듬기, 애매함 판단) 쓰고, 설명은 내가 쓴 문서에서만 나온다. ① 의미 검색 → 질문 다듬기 → ② RAG | 지어낸 답을 막는다. ①만으로도 "검색어를 모르는" 문제는 풀린다 |
| 데이터 (D-047) | 크롤링 없이 공식 출처를 보고 직접 쓰거나 필요한 표만 옮긴다. 2026 시즌 확정 기록 기준 | KBO 공식 사이트는 사전 승인 없는 자동 수집을 금지한다(`robots.txt`). MVP 기간이 비시즌이라 기록이 바뀌지 않는다 |
| 기록 읽는 법 (D-048) | 1차 스탯 기준표(예: 타율 .300 이상 = 3할 타자) + "한 단계 더"(OPS·WAR). 표현과 풀이는 내가 쓴다 | 뉴비가 보는 숫자는 전광판의 1차 스탯이다. 오래 본 사람의 말투가 포털과의 차이가 된다 |
