## D-014 SDD 툴 없이 단계를 직접 구성한다
- 날짜: 2026-11-12
- 상태: 유효
- 문제: SDD 툴(예: Spec Kit)을 쓸지, 방식을 직접 만들어 AI에게 알려 줄지. 그리고 어떤 단계로 진행할지 (출처: 나, AI 보완 / 영향도: 높음)
- 옵션: A SDD 툴 도입 / B 직접 구성 (툴의 흐름과 템플릿만 빌려 옴)
- 선택: B. 단계는 다음과 같다.
  1. 대원칙 정의: 기본 기술스택, 기획/설계 산출물 형식과 도구(화면, 와이어프레임, ERD, API 등), 테스트 방식과 목적
  2. 기능(스펙) 정의: 기능마다 수용 기준을 함께 쓴다
  3. 개발 계획: 1, 2를 바탕으로 만든다
  4. 개발 작업 생성: 2, 3을 바탕으로 만들고, 작업마다 테스트를 먼저 정한다
  5. 개발 실행
  6. 검증·테스트: 수용 기준과 평가 질문 세트로 확인한다
  - 단계 사이에는 내 승인이 있어야 다음 단계로 간다. 뒤 단계에서 앞 단계가 틀린 걸 발견하면 앞 단계 문서부터 고친다.
- 근거:
  - 이 프로젝트의 1순위 목표가 기획/설계를 새로운 방식으로 준비해 보는 것이다 (D-003). 툴을 쓰면 방식은 툴이 정한 게 된다. 직접 만들면 방식을 고르고 다듬는 과정 자체가 결과물이 된다.
  - CLAUDE.md, plan.md, 지우지 않는 결정 로그, 작업 단위 폴더(D-011, D-012)를 이미 갖췄다. 툴을 넣으면 자체 폴더와 원칙 문서가 이것과 겹친다.
  - Claude Code Pro 한도를 채팅과 개발에 같이 쓴다. 문서를 많이 만드는 툴은 부담이 크다.
- 비고 (AI 보완, 채택):
  - 기술스택 중 기능에 따라 달라지는 것(LLM 제공사, 벡터 저장소 등)은 대원칙이 아니라 3단계 개발 계획에서 정한다.
  - 대원칙에는 도구보다 산출물 형식을 둔다. 다음 단계의 AI가 읽을 수 있도록 레포 안에 텍스트로 둔다(예: ERD는 Mermaid, API는 OpenAPI).
  - 테스트는 두 층으로 나눈다: 기능 테스트(자동, CI) / AI 설명 품질 평가(평가 질문 세트, 사람 검수).
  - 자동화(커스텀 명령 등)는 아직 정하지 않았다.

## D-015 1주차 목표를 설계 산출물까지로 넓힌다
- 날짜: 2026-11-12
- 상태: 유효
- 문제: 기존 1주차 계획(고객·목적 확정, 설문, SDD 조사)보다 1주차에 끝낼 범위가 넓어졌다 (출처: 나 / 영향도: 높음)
- 옵션: 기존 일정 유지 / 1주차에 설계 산출물까지 끝낸다
- 선택: 1주차에 끝낸다. 주제와 MVP 핵심 기능(3개 이하) 확정, ERD·API 설계, 와이어프레임, 배포 시스템 아키텍처, 기술스택 결정, 저장소 구조, CI 뼈대(빌드·테스트 자동 실행). 작업표는 이 폴더의 `plan.md`.
- 근거: 1주차에 해야 할 일로 위 목록을 정했다. 기능 정의와 프론트엔드·DB 결정이 2주차에서 1주차로 당겨진다.
- 영향:
  - `docs/plan.md`의 1주차 목표와 실행 전제(프론트엔드·DB 결정 시점)를 고쳤다.
  - AI 구성(RAG) 세부 사항은 2주차 말 확정을 유지한다. 1주차에는 ERD를 그리는 데 필요한 만큼만 가정한다.
  - 설문은 1주차에 돌려 두고 2주차 평가 질문 세트에 반영한다.
  - 2주차 계획은 다시 짜야 한다 (남은 것).

## D-016 SDD 단계는 기능 단위로 돈다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: D-014의 단계를 프로젝트 전체에 한 번만 적용하면 설계가 모두 끝나야 개발을 시작할 수 있다. 스터디에서는 1주차에 계획/설계 상당 부분을 끝내되 2주차까지 이어져도 된다고 했다 (출처: 스터디 회의 → AI 제안 → 나 보완·결정 / 영향도: 높음)
- 옵션: A 전체를 한 번에 진행 (설계 완료 후 개발) / B 기능 단위로 진행
- 선택: B
  - 한 번만 정하는 것: 대원칙, MVP 기능 목록과 "안 할 것", 아키텍처 큰 그림, 레포·CI
  - 1주차에 모든 기능의 개요를 정한다: 목적, 사용자 흐름, 들어갈 것과 뺄 것, 다루는 데이터, 필요한 화면·API 목록. 이를 바탕으로 전체 설계 초안을 만든다 (ERD는 엔티티와 관계, API는 엔드포인트 목록, 화면은 목록과 흐름).
  - 개요의 깊이 기준: 그 기능에 어떤 ERD(엔티티)와 API가 필요할지 짐작할 수 있을 정도.
  - 개요에는 규모(엔티티·API·화면 수와 대략의 작업량)를 함께 적고, 이를 시간 예산과 비교해 MVP 범위를 자르는 근거로 쓴다.
  - 기능마다 도는 것: 상세 명세(수용 기준, 예외, 평가 질문 연결) → 상세 설계(필드·요청/응답·화면 상세) → 작업 → 구현 → 검증
  - 1주차에는 F1의 상세 명세와 상세 설계까지 끝낸다. F2·F3의 상세는 2주차로 이어질 수 있다.
  - 지킬 선: 대원칙은 첫 코드 전에 끝낸다. 어떤 기능도 명세 없이 구현하지 않는다. ERD·API를 고칠 때는 해당 기능 명세부터 고친다(D-014). F1에 필요한 AI 구성은 F1 구현 전에 정한다.
- 근거:
  - 요즘은 AI로 기획/설계를 당길 수 있어서, 스터디에서 1주차에 상당 부분을 끝내고 2주차까지 이어지는 방향으로 해 보기로 했다. SDD의 명세 단위는 보통 기능 하나라서 이 방향과 맞고, 주차별로 기능을 넓혀 가는 일정과도 맞는다. 기능별 작업 단위 폴더(D-012)와도 맞는다.
  - 전체 기능의 윤곽이 있어야 ERD·API·화면을 한 그림으로 잡을 수 있고, 프로젝트 규모를 짐작해 일정을 관리할 수 있다. (출처: 나)
- 비고: D-014를 대체하지 않고 보충한다. 기능별 작업 단위 폴더는 `docs/specs/<날짜>-F1-<이름>/` 형식으로 만든다.
