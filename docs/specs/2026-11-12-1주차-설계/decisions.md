## D-014 SDD 툴 없이 단계를 직접 구성한다
- 날짜: 2026-11-12
- 상태: 유효
- 문제: SDD 툴(예: Spec Kit)을 쓸지, 방식을 직접 만들어 AI에게 알려 줄지. 그리고 어떤 단계로 진행할지 (출처: 나, AI 보완 / 영향도: 높음)
- 옵션: A SDD 툴 도입 / B 직접 구성 (툴의 흐름과 템플릿만 빌려 옴)
- 선택: B. 단계는 다음과 같다.
  1. 대원칙 정의: 기본 기술스택, 기획/설계 산출물 형식과 도구(화면, 와이어프레임, ERD, API 등), 테스트 방식과 목적
  2. 기능(스펙) 정의: 기능마다 수용 기준을 함께 쓴다
  3. 개발 계획: 1, 2를 바탕으로 만든다
  4. 개발 작업 생성: 2, 3을 바탕으로 만들고, 작업마다 테스트를 먼저 정한다
  5. 개발 실행
  6. 검증·테스트: 수용 기준과 평가 질문 세트로 확인한다
  - 단계 사이에는 내 승인이 있어야 다음 단계로 간다. 뒤 단계에서 앞 단계가 틀린 걸 발견하면 앞 단계 문서부터 고친다.
- 근거:
  - 이 프로젝트의 1순위 목표가 기획/설계를 새로운 방식으로 준비해 보는 것이다 (D-003). 툴을 쓰면 방식은 툴이 정한 게 된다. 직접 만들면 방식을 고르고 다듬는 과정 자체가 결과물이 된다.
  - CLAUDE.md, plan.md, 지우지 않는 결정 로그, 작업 단위 폴더(D-011, D-012)를 이미 갖췄다. 툴을 넣으면 자체 폴더와 원칙 문서가 이것과 겹친다.
  - Claude Code Pro 한도를 채팅과 개발에 같이 쓴다. 문서를 많이 만드는 툴은 부담이 크다.
- 비고 (AI 보완, 채택):
  - 기술스택 중 기능에 따라 달라지는 것(LLM 제공사, 벡터 저장소 등)은 대원칙이 아니라 3단계 개발 계획에서 정한다.
  - 대원칙에는 도구보다 산출물 형식을 둔다. 다음 단계의 AI가 읽을 수 있도록 레포 안에 텍스트로 둔다(예: ERD는 Mermaid, API는 OpenAPI).
  - 테스트는 두 층으로 나눈다: 기능 테스트(자동, CI) / AI 설명 품질 평가(평가 질문 세트, 사람 검수).
  - 자동화(커스텀 명령 등)는 아직 정하지 않았다.

## D-016 SDD 단계는 기능 단위로 돈다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: D-014의 단계를 프로젝트 전체에 한 번만 적용하면 설계가 모두 끝나야 개발을 시작할 수 있다. 스터디에서는 1주차에 계획/설계 상당 부분을 끝내되 2주차까지 이어져도 된다고 했다 (출처: 스터디 회의 → AI 제안 → 나 보완·결정 / 영향도: 높음)
- 옵션: A 전체를 한 번에 진행 (설계 완료 후 개발) / B 기능 단위로 진행
- 선택: B
  - 한 번만 정하는 것: 대원칙, MVP 기능 목록과 "안 할 것", 아키텍처 큰 그림, 레포·CI
  - 1주차에 모든 기능의 개요를 정한다: 목적, 사용자 흐름, 들어갈 것과 뺄 것, 다루는 데이터, 필요한 화면·API 목록. 이를 바탕으로 전체 설계 초안을 만든다 (ERD는 엔티티와 관계, API는 엔드포인트 목록, 화면은 목록과 흐름).
  - 개요의 깊이 기준: 그 기능에 어떤 ERD(엔티티)와 API가 필요할지 짐작할 수 있을 정도.
  - 개요에는 규모(엔티티·API·화면 수와 대략의 작업량)를 함께 적고, 이를 시간 예산과 비교해 MVP 범위를 자르는 근거로 쓴다.
  - 기능마다 도는 것: 상세 명세(수용 기준, 예외, 평가 질문 연결) → 상세 설계(필드·요청/응답·화면 상세) → 작업 → 구현 → 검증
  - 1주차에는 F1의 상세 명세와 상세 설계까지 끝낸다. F2·F3의 상세는 2주차로 이어질 수 있다.
  - 지킬 선: 대원칙은 첫 코드 전에 끝낸다. 어떤 기능도 명세 없이 구현하지 않는다. ERD·API를 고칠 때는 해당 기능 명세부터 고친다(D-014). F1에 필요한 AI 구성은 F1 구현 전에 정한다.
- 근거:
  - 요즘은 AI로 기획/설계를 당길 수 있어서, 스터디에서 1주차에 상당 부분을 끝내고 2주차까지 이어지는 방향으로 해 보기로 했다. SDD의 명세 단위는 보통 기능 하나라서 이 방향과 맞고, 주차별로 기능을 넓혀 가는 일정과도 맞는다. 기능별 작업 단위 폴더(D-012)와도 맞는다.
  - 전체 기능의 윤곽이 있어야 ERD·API·화면을 한 그림으로 잡을 수 있고, 프로젝트 규모를 짐작해 일정을 관리할 수 있다. (출처: 나)
- 비고: D-014를 대체하지 않고 보충한다. 기능별 작업 단위 폴더는 `docs/specs/<날짜>-F1-<이름>/` 형식으로 만든다.

## D-019 DB는 PostgreSQL + pgvector로 한다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: DB 종류. 회원 정보가 중요하지 않을 수 있어 RDBMS가 아니어도 되지 않을까 (출처: 나 → AI 비교 → 나 결정 / 영향도: 높음)
- 옵션: PostgreSQL + pgvector / MySQL / MariaDB / MongoDB
- 선택: PostgreSQL + pgvector
- 근거:
  - 이 서비스의 DB 선택 기준은 회원 정보가 아니라 RAG의 벡터 검색이다. 저장할 데이터는 근거 문서와 임베딩(벡터 검색), 질문 로그·답변·피드백(형태가 바뀔 수 있음), 팀 정보(정형, 점수 계산)다.
  - PostgreSQL + pgvector는 셋을 DB 하나로 처리한다. 형태가 바뀌는 데이터는 JSONB로 유연하게 둔다. JPA를 그대로 쓰고, Spring AI 지원이 가장 많다. Docker 이미지(`pgvector/pgvector`)로 바로 띄운다.
- 고르지 않은 이유:
  - MySQL: 무료판은 벡터 저장만 되고 거리 계산·벡터 인덱스가 없다(2026-11 기준, 고를 때 다시 확인 필요). 규모가 작아 앱에서 직접 계산할 수는 있지만 검색 코드를 직접 짜야 한다.
  - MariaDB: 벡터 검색과 Spring AI 지원이 있어 차선책이었다. MySQL 문법이 필요한 이유가 없어 PostgreSQL을 골랐다.
  - MongoDB: 벡터 검색은 주로 Atlas(관리형) 기능이라 EC2에 직접 띄우면 벡터 저장소를 따로 둘 가능성이 크다.
- 영향: 1주차 작업표 3-2에서 정하려던 벡터 저장소가 pgvector로 정해졌다. 3-2에는 LLM 제공사와 임베딩 방식이 남는다.

## D-020 인프라는 AWS 무료 플랜 안에서 EC2 1대 + Docker Compose로 한다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: 배포 인프라. AWS 신규 가입으로 크레딧 100달러가 생겼다 (출처: 나, AI 보완 / 영향도: 높음)
- 옵션: EC2 + Docker + Jenkins / EC2 1대 + Docker Compose (빌드는 외부)
- 선택: EC2 1대에 Docker Compose로 nginx(React 정적 파일 + /api 프록시), Spring Boot, PostgreSQL + pgvector를 띄운다. AWS 무료 플랜 크레딧을 넘지 않는다.
- 근거:
  - 서버 한 대에 모으면 비용과 운영 부담이 가장 적다 (D-017).
  - 대략 비용 (서울 리전, 온디맨드, EBS·공인 IP 포함): t3.small(2GB) 6주 약 37달러, t3.medium(4GB) 약 65달러. t3.small은 빠듯해서 스왑을 설정한다.
- 확인할 것: 가입된 플랜 종류와 기한, 무료 플랜에서 고를 수 있는 인스턴스 타입, 결제 알림(Budget) 설정, 이 크레딧을 서비스용 AI(Bedrock)에 쓸 수 있는지.

## D-021 CI/CD는 GitHub Actions로 한다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: CI/CD 도구 (출처: 나는 Jenkins 검토 → AI 제안 → 나 결정 / 영향도: 중간)
- 옵션: Jenkins / GitHub Actions
- 선택: GitHub Actions. 빌드·테스트(CI) → Docker 이미지 빌드·레지스트리 푸시 → SSH로 EC2에 배포(CD)
- 근거:
  - Jenkins 자체가 메모리를 1~2GB 쓴다. 같은 EC2에 두면 서비스 메모리가 모자라고, 따로 띄우면 크레딧이 두 배로 든다.
  - 빌드를 GitHub에서 하므로 EC2가 가벼워진다.
  - 스터디 회의안의 "작업은 GitHub Issues, PR이 Issue를 닫는다" 흐름과 GitHub 안에서 이어진다.
- 고르지 않은 이유: Jenkins 경험 자체는 이 프로젝트의 목표 우선순위(D-003)에 없다.

## D-023 와이어프레임은 Stitch로 만들고, 프롬프트와 결과를 레포에 남긴다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: 화면·와이어프레임을 만들 도구 (출처: AI 제안(HTML 목업) → 나 제안(Stitch, Figma Make, v0) → 나 결정 / 영향도: 중간)
- 옵션: Claude HTML 목업 / Google Stitch / Figma / Excalidraw / Figma Make / v0
- 선택: Google Stitch. 규칙은 다음과 같다.
  1. 입력은 명세다. `screens.md`나 기능 명세의 화면 설명으로 프롬프트를 쓴다.
  2. 프롬프트를 `wireframe/prompt.md`에 남긴다.
  3. 내보낸 HTML과 캡처를 `wireframe/`에 저장한다.
  4. 기준은 명세다. 디자인과 명세가 다르면 명세를 먼저 고치거나(D-014) 다시 생성한다. 구현 때 Claude Code는 명세와 이 HTML을 함께 참고한다.
- 근거:
  - AI 디자인 도구를 써 본다는 대원칙의 의도에 맞는다. 결과를 HTML로 받아 레포에 둘 수 있다.
  - Claude HTML 목업보다 화면 완성도가 높아 발표 자료로 좋다. 무료다 (D-017).
- 고르지 않은 이유:
  - Figma Make, v0: 화면 디자인이 아니라 화면 코드를 만든다. 구현 단계의 Claude Code와 역할이 겹치고, "명세 → AI 구현" 흐름과 그 효과 비교(Verification)가 흐려진다. v0는 Tailwind·shadcn/ui·Next.js 구조를 함께 정해 버린다.
  - Figma: 결과물이 레포 밖에 있다.
  - Excalidraw, Claude HTML 목업: 레포에 둘 수 있지만 화면 완성도가 낮다.
- 비고: 도구의 기능과 요금은 자주 바뀌므로 처음 쓸 때 확인한다. 같은 화면을 Stitch, v0, Claude로 만들어 비교하는 실험은 여유가 있을 때 한다.

## D-025 API 명세는 레포의 OpenAPI 파일을 원본으로 두고, Notion에 동기화한다
- 날짜: 2026-11-13
- 상태: 유효
- 문제: API 명세 형식과 위치. 보통 Notion에 쓰는데, AI가 만든 명세를 Notion에 옮기는 수작업이 생긴다 (출처: 나 → AI 제안 → 나 결정 / 영향도: 중간)
- 옵션: A 레포가 원본, Notion은 보기용 사본 / B Notion이 원본
- 선택: A
  - 전체 엔드포인트 목록은 Markdown 표로, 기능 상세는 OpenAPI 3 yaml로 쓴다 (D-016의 두 깊이).
  - Notion에는 AI가 내가 써 온 템플릿 형식으로 옮긴다. 기능 상세 설계를 승인할 때 반영한다.
  - Notion 페이지 맨 위에 "원본은 레포의 OpenAPI 파일. 여기서 직접 수정하지 않음"이라고 적는다. 고칠 것은 레포에서 고친다.
- 근거:
  - 구현하는 AI와 CI가 레포 파일을 바로 읽는다. 구현 후 springdoc 결과와 비교해 명세와 코드가 맞는지 검사할 수 있다(1-3과 연결).
  - 변경 이력이 git과 결정 기록으로 이어진다.
  - Notion 연결로 옮기는 일을 AI가 하므로 수작업이 없다. 스터디 회의안의 "기술 기록은 저장소, 공유는 Notion"과도 맞는다.
- 고르지 않은 이유: B는 AI가 구현할 때마다 Notion을 불러와야 해 사용량이 늘고, CI가 읽기 어렵고, 레포 기준 원칙(D-014)과 어긋난다.
- 남은 것: Notion 템플릿 확인과 레포↔Notion 항목 대응 규칙, 만들 위치(공용 스터디 / 개인), API 외 문서도 올릴지.
