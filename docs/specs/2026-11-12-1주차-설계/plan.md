# plan.md (1주차 설계)

> 작업 단위: 1주차 기획/설계. 전체 계획은 `docs/plan.md`. 이 단위의 결정은 같은 폴더의 `decisions.md`.

## 목표

1주차 안에 아래를 끝낸다. (D-015)
- 주제와 MVP 핵심 기능(3개 이하) 확정, 모든 기능의 개요(규모 포함), F1 상세 명세 (D-016)
- 전체 설계 초안(ERD·API·화면)과 F1 상세 설계, 배포 시스템 아키텍처
- 기능 구현에 맞는 기술스택 결정
- 저장소 구조, CI 뼈대(빌드·테스트 자동 실행)

## 진행 방식

자체 SDD 구성(D-014)을 따른다.
1. 대원칙 정의 → 2. 기능(스펙) 정의 → 3. 개발 계획 → 4. 개발 작업 생성 → 5. 개발 실행 → 6. 검증·테스트
- 1단계(대원칙)는 한 번 정하고, 2~6단계는 기능마다 돈다. 단, 모든 기능의 개요와 전체 설계 초안은 1주차에 만든다. (D-016)
- 단계 사이에는 내 승인이 있어야 다음 단계로 간다.
- 뒤 단계에서 앞 단계가 틀린 걸 발견하면 앞 단계 문서부터 고친다.
- 담당 표기: "나 결정" = 내가 직접 정한다 / "AI 초안 → 나 승인" = AI가 쓰고 내가 승인한다 / "AI" = AI가 처리한다

## 진행 흐름

```
0 → 1-1, 1-2 → 1-3 → 2-3 ──────────┐
     2-1 → 2-2a → 2-2b ────────────┴→ 2-4 → 3-1, 3-2 → 3-3 → 3-4
1-1 → 4-1 → 4-2 → 4-3 (2·3단계와 동시에 진행 가능)
```

- 핵심 경로는 2-2a(기능 확정) → 2-2b(전체 개요) → 2-4(F1 상세 명세)다. 와이어프레임·ERD·API가 모두 여기에 걸린다. 대원칙에서 오래 붙잡지 않는다.
- 2-2b의 규모 추정을 시간 예산과 비교해 기능을 자른다. 이를 위해 주당 투입 시간이 필요하다.
- 4단계는 1-1이 끝나면 따로 진행할 수 있다.
- 시간이 모자라면: 와이어프레임은 화면 목록과 흐름만, 아키텍처는 다이어그램 한 장만 남긴다.
