## D-011 SDD 방식으로 진행하고, 세부 운영은 레포에서 정하며 기록한다
- 날짜: 2026-11-12
- 상태: 유효
- 문제: 개발 방식 (출처: 나, 네이버 현업 사례 참고 / 영향도: 높음)
- 선택: LLM과의 기획/설계 대화를 `plan.md`, `decisions.md`로 저장하고 후속 개발에 활용한다. 한 번 기재된 결정은 지우지 않는다. 모델이 바뀌어 규칙을 덜어내면 그 이력도 남긴다.
- 근거: 시행착오를 남기고 참조를 편하게 한다. 방식을 정하는 과정도 기록으로 남기기 위해, 다 정하고 시작하지 않고 레포부터 만든다.

## D-012 문서를 작업 단위별 폴더로 나눈다
- 날짜: 2026-11-12
- 상태: 유효
- 문제: plan.md와 decisions.md를 파일 하나에 계속 쌓을지, 작업 단위로 나눌지 (출처: 나 / 영향도: 중간)
- 옵션: A 작업 단위별 폴더 / B 날짜별 파일 / 단일 파일 유지
- 선택: A. `docs/specs/<날짜-작업명>/plan.md`, `decisions.md`. 전체 6주 계획은 `docs/plan.md`에 하나 둔다. 결정 번호(D-000)는 프로젝트 전체에서 이어 매긴다. `docs/decisions.md`는 전체 결정의 목차(번호, 제목, 위치)만 둔다.
- 근거: SDD는 작업 단위로 명세를 쓰므로 한 작업의 결정과 시행착오가 한곳에 모인다. AI가 필요한 폴더만 읽어 컨텍스트가 가볍다. 번호를 이어 매기면 폴더를 넘는 대체 참조(D-006이 D-005를 대체)가 헷갈리지 않는다.
- 비고: D-001~D-011은 내용을 바꾸지 않고 두 폴더로 옮겼다. 상태 변경은 각 결정이 있는 폴더 파일에서만 한다. 목차에는 상태를 적지 않는다.
